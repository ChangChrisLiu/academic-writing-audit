# 审稿回复：把问题回答清楚，把正文改清楚

[返回主页](../README.md) · [中文说明](../README.zh-CN.md) · [安装 reviewer-response-writing](../skills/reviewer-response-writing/SKILL.md)

这份指南总结实际 rebuttal 写作及后续稿件审查中的经验。既保留有效做法，也吸收回复后仍未解决的问题。下面的例子全部是虚构情境，不是原始论文或审稿通信的摘录。

## 1. 先回答实质问题，再组织礼貌表达

“感谢审稿人的宝贵意见”不能替代答案。先判断对方真正想知道什么：方法究竟做了什么，比较是否支持结论，证据是否充分，还是正文没有把已有内容讲清楚？

局部回应通常可按 **直接回答 → 对应证据 → 允许得出的结论与边界 → 修改或待办** 组织。它不是固定四句话模板；一句能说明的定义，不需要扩成一段答辩。

例如，对“固定基线是什么”的回答，先写输入、评分规则以及如何拟合模型，再解释结果差异。一个含混的基线名称加一串表格数字，仍然没有回答比较对象的问题。

## 2. 按主题合并，同时保留逐条覆盖

短 rebuttal 可以把共同问题组织成“基线定义与比较”“敏感性分析”“消融与归因”“验证指标”“实现细节”等主题。标题要帮助审稿人找到答案，并保留对应意见编号。

内部维护一个简短映射：

| 意见 | 实质问题 | 证据与位置 | 回应动作 | 当前状态 | 未解决事项 |
| --- | --- | --- | --- | --- | --- |
| R1-Q1 | 基线的评分规则是什么？ | 当前 Methods 的定义 | 澄清 | 源码已核对 | 最终页码待编译 |
| R2-Q2 | 标注噪声会影响训练吗？ | 只有标注者一致性结果 | 限定结论 | 未做噪声实验 | 对训练影响未知 |

主题式写法不能吞掉小问题。阈值、成功定义的位置、术语、百分比表述和图表格式等具体要求，也应有明确处理结果。

## 3. 证据回答哪个问题，就写到哪里

原始评测、新增压力测试、敏感性分析和内部验证指标分别回答不同问题。可以互相补充，但不能合并分母，也不能用新实验的置信区间替原始实验完成显著性判断。

同样需要区分：

| 已有证据 | 可以说明 | 仍不能直接说明 |
| --- | --- | --- |
| 完整方法优于固定基线 | 该评估下整体流程的比较结果 | 单独的选择步骤造成了多少增益 |
| 多位标注者较一致 | 指定规则下的标注一致性 | 训练对错误标注是否稳健 |
| 若干训练种子结果接近 | 已测试条件下的运行差异 | 整个模型选择过程普遍稳定 |
| 扰动差异的区间跨零 | 当前估计及其不确定性 | 等效、没有影响或全面鲁棒 |
| 验证候选排序接近 | 该指标下的候选区分情况 | 对真实部署表现的预测已校准 |

不要为了显得有说服力而加强归因。也不要把所有解释都删成报数：保留结果对研究问题的意义，把尚未隔离的机制讲准确。

## 4. 不能完成的实验，诚实限定结论

对尚未开展的实验，可以说明现有证据回答了哪一部分、剩下什么问题，以及是否需要缩小主张。新实验不是每一条审稿意见的默认答案。

“建议补做”“作者计划开展”“作者报告已完成”“已经核对实验或稿件记录”是不同状态。没有作者确认，不替作者承诺新数据、新平台或新的研究计划；没有证据，不把计划改写成结果。

也要区分“没有提供给 agent”和“研究没有开展”。例如，输入中没有置信区间，并不意味着作者没有做过不确定性分析。把需要补充材料的问题放入单独的作者核对项；正文和回复信只陈述已知结果与确认过的限制。

合理不同意时，明确指出需要区分的前提或研究范围，并给依据。即使实质判断成立，也要检查原文是否容易让读者产生同样的误解。

## 5. Response letter 与 rebuttal 使用不同篇幅结构

**短 rebuttal** 根据给定的字数或页数限制优先回答影响核心贡献的问题，允许时合并共同主题，利用紧凑表格减少重复。先核对该 venue 是否允许新结果、附件或稿件修改。

**逐点 response letter** 保留意见编号，逐条给直接回应、证据和实际修改位置；必要时引用核对过的改后文字。没有最终页码时先用已核实的小节名，或者显式标记待补，不编造行号。

是否需要 cover letter、是否要求标色、不同审稿人能否看到彼此的意见，都依据实际投稿要求。不要把某次投稿的排版习惯变成所有 agent 必须遵守的规则。

## 6. 回复信解释修改，正文解释研究

假设已核对 Methods 确实完成修改：

**回复信**

> 该基线采用预设线性评分与固定组别系数，并拟合一个模型。我们已在 Methods 的 Comparators 小节补充这一操作定义。

**正文**

> 该基线采用预设线性评分与固定组别系数，并拟合一个模型。

正文不需要“为回应审稿人”“我们现已澄清”“不存在审稿人担心的问题”等交代过程的表达。它需要的是完整、直接、可独立阅读的科学说明。必要的否定、限制和不确定性要保留。

若还未改文件，回复草稿就应写“拟补充”，并将候选正文单独标注为建议。正式完成后，再核对两份材料是否一致。

有用的 rebuttal 分析可以进入 Results，例如解释不同数据来源的作用或比较在哪种测试条件下更明显；迁移的是有依据的科学内容，不是回应审稿人的口吻。

## 7. 最后检查实际稿件

一封清楚的回复信，不能证明正文已经清楚。重读改后的方法入口、首次定义、结果解释以及相关图表，检查必要说明是否出现在读者真正需要的位置。

确认回复中每个“已修改”都对应当前版本的真实变更；数值、引用、图表、小节和精确引文一致。源码核对、编译成功、PDF 视觉检查和提交成功分别记录，不合并成一个没有依据的“完成”。

## 可直接使用的请求

```text
使用 $reviewer-response-writing，参考这份真实审稿意见与当前稿件，
起草 [短 rebuttal / 逐点 response letter]。以下是投稿限制和证据。
先映射每条意见的实质问题，必要时按主题合并，但不要遗漏具体请求。
区分原始评测、新实验和验证分析；不做证据不支持的因果归因。
每条回应标明已完成的修改或仍需作者提供的材料。
单独给出建议的正文替换，让未读过审稿意见的人也能直接理解。
```

如果只需要判断正文该怎么改，用 [reviewer-comment-triage](../skills/reviewer-comment-triage/SKILL.md)；如果只需处理防御性语气，用 [nondefensive-writing](../skills/nondefensive-writing/SKILL.md)。不必为了一个局部问题加载整套 skills。

## 回复中的自然表达

回复信同样需要明确的主语、具体的证据和简单可读的句式。直接回答问题，避免每段重复感谢、强调重要性或宣称充分证明。按作者要求使用连贯段落，默认不用解释性冒号和句中破折号。逐点回复可用独立的小标题保留评论编号，评论原文和实际修改引文则保持准确。

长句拆分后仍需保留范围和条件。同一组结果可以在回复中集中说明并交叉引用，但每条独立请求都要有交代。正文只保留读者需要的研究解释，不复制回复中的感谢、修改过程和 reviewer 指代。更多例子见[自然表达与逻辑审查指南](prose-guide.md)。
